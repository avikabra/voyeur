# site/

The Voyeur catalog. A static site generated by one zero-dependency Node script.

It reads every `apps/*/manifest.json` in the repo (plus the optional `site/coming.json`) and writes plain HTML into `site/dist/`. There is no package.json, no npm install, no framework, no build tooling. `node site/build.js` works from a clean clone with nothing but Node 18+, which is the point: the pipeline runs unattended and a broken toolchain has nobody to fix it.

## Build

```
node site/build.js
```

Works from the repo root or from inside `site/` — the script resolves the repo root from its own location.

Output lands in `site/dist/` (gitignored, rebuilt from scratch on every run):

```
dist/
├── index.html              the tile grid, newest first
├── about/index.html        what Voyeur is, in a dozen lines
├── apps/<slug>/index.html  one detail page per app
├── apps/<slug>/app/        the app itself, copied verbatim
├── 404.html
├── robots.txt
└── sitemap.xml             only when SITE_URL is set
```

Flags and env:

| | |
|---|---|
| `--strict` | exit non-zero if any manifest produced a warning. For local checking only — the unattended pipeline should **not** use this, since a warning must never block a deploy. |
| `SITE_URL` | absolute origin. Production is `https://voyeur-catalog.vercel.app`. When set, canonical `<link>` tags and a `sitemap.xml` are emitted. Unset by default: a wrong canonical URL is worse than none. |
| `BASE_PATH` | prefix for every internal link when the site is served from a subpath. Empty (site root) by default, which is what Vercel needs. |

## Preview

```
npx serve site/dist
# or, no npm at all:
python3 -m http.server -d site/dist 8000
```

Check it at 375px wide first. Most fashion problems happen while standing in a store.

## Deploy

Its own Vercel project at **https://voyeur-catalog.vercel.app**, separate from every app, per `docs/ARCHITECTURE.md`. Build command `node site/build.js`, output directory `site/dist`, no install step. Rebuild and redeploy after every ship so new entries appear.

## What it reads

`apps/<slug>/manifest.json` is the only interface between an app and this site — there is no other registration step. The schema and field notes live in [`docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md#manifestjson--the-contract).

What the builder does with it:

- **Required to render:** `slug`, `name`, `need`, `status`. A manifest missing any of these is skipped with a warning.
- **Optional, degrades quietly:** `description`, `limitations`, `evidence`, `liveUrl`, `created`, `updated`, `tech`, `localRun`, `license`.
- **Bad input never kills the build.** Unparseable JSON, a missing manifest, an unusable slug — the app is skipped, a loud warning is printed, and every other app still ships. One bad file must not cost us the catalog.
- **Unknown `status` values become `wip`**, never `live`. Guessing "live" on a malformed manifest would publish a claim we can't stand behind.
- **`liveUrl` must be http(s).** Anything else (`javascript:`, `data:`) is dropped and the tile links to the detail page instead.
- **Everything from a manifest is HTML-escaped** on the way out. Manifests are written by agents and are a real injection path.
- **Empty `limitations` on a live or broken app warns**, and the detail page says the limitations weren't declared rather than implying there are none. See `docs/PRINCIPLES.md` on honesty.
- **Sort order** is `created` descending, undated last.

## `site/coming.json` — the "In the works" tiles

Optional. An array of the builds the pipeline has already committed to, so the grid shows the real near future instead of a lonely single tile:

```json
[{ "title": "Virtual try-on in the browser", "need": "See a garment on you without an app, an account or a paid GPU." }]
```

- **Missing file = no tiles and no warning.** A clone without it still builds a clean catalog.
- A file that *exists* but is unparseable, isn't an array, or has an entry missing `title` or `need` **does** warn — that is a mistake, not a choice — and the bad entry is skipped.
- These tiles are muted, dashed and contain **no link at all**, because there is nothing to open yet. They carry an "In the works" chip.
- Keep it in step with the owner-directed priorities at the top of `pipeline/state/backlog.md`, and delete an entry when the app ships (its real tile replaces it).

## Design

Light mode only. A tile grid you click, not a page you read.

- **Home** opens with a compact hero band: the wordmark (accent mark + tight, heavy type), the one-line tagline, and a count line derived from the real data (`1 live tool · 2 in build`). One headline, one support line, one stat — no essay.
- **Tiles** carry an app name, the `need` one-liner, a status chip, and a small identity mark: the app's initial in a disc tinted with an accent hue hashed from its slug (FNV-1a, clamped to 200–349° so everything stays in the house blue-to-magenta family). The same hue draws the tile's 3px top rule, its live chip and the top rule of its detail page.
- The whole tile is the click target and it goes **straight to the app** (`liveUrl`); a small secondary "Details" link goes to the detail page. Broken and retired apps get a muted tile whose click target is the detail page, not a link we know is dead — done with a stretched `::after` on the title anchor, so there are no nested `<a>` elements and no JavaScript.
- **Detail pages** are compact: name, need, "Open the app", then What it does, Limitations, Who asked, Run locally, source, dates — sections separated by hairlines on a shared type scale.
- One column below ~28rem, filling to 4 columns on a wide screen via `auto-fit` / `minmax`. The grid's width is capped from the real tile count (`--n`) so one or two tiles don't stretch into billboards. No horizontal scroll at 375px.
- All CSS is inlined in the page; the favicon is an inline `data:` SVG of the same mark. No external stylesheets, no webfonts, no CDNs, no third-party requests of any kind — a loaded page makes exactly one request, for itself.
- No JavaScript. A static list does not need hydration.
- System font stack, one accent colour plus the per-app hue, no dark-mode variant (`prefers-color-scheme` appears nowhere).
- All text meets WCAG AA (≥4.5:1), including every hue in the generated range; status chips are labelled, never colour-only; focus is a visible 2px accent ring.
- Semantic HTML, real `<a href>` links, one `<title>` and `<meta name="description">` per page.

## Adding a page type

Everything lives in `build.js`: `CSS`, `layout()`, and one `render*()` function per page. Add a renderer, call `writeFile()` for it in `build()`. Keep it dependency-free.
