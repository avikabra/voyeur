## Addendum (same session, interactive follow-up) — rendering quality was not actually good enough

The owner reviewed the verification screenshot posted above and called the overlay quality
disqualifying — correctly. The mistake: I verified *functional* correctness (no crashes, no
console errors, sensible size/placement) and treated that as "the adversarial loop already
covered this," without separately judging whether the composited image looked like something
a stranger would want. It didn't. This is exactly the PRINCIPLES failure mode of confusing
mechanical checks with the actual bar ("would a stranger want this and would it work for them").
Neither this run's local re-verification nor the previous run's adversarial-loop rounds had a
visual-quality check as its own category — worth naming as a gap in how this app's adversarial
loop was run, for whoever revisits the process.

**Researched AI image generation, at the owner's suggestion, before ruling it out.** Findings,
dated 2026-08-10:
- Every fast/small diffusion model with public weights (SD-Turbo, SDXL-Turbo) is licensed
  non-commercial-only (Stability AI Non-Commercial Research Community License) — disqualifying,
  same reasoning as the CC-BY-NC-SA VTON models already rejected in RESEARCH.md.
- The permissively-licensed ones (FLUX.1-schnell, Qwen-Image 2.0, HiDream — Apache/MIT) are
  6–8B-parameter frontier models, multi-GB, GPU-class. Not close to phone/browser feasible.
- Google's MobileDiffusion and Meta's SnapFusion (genuinely mobile-optimized, sub-second)
  are research papers with no public weight release found — nothing to legally bundle.
- Investigated a non-generative alternative: u2netp, a 4.7MB MIT-licensed salient-object
  segmentation model, as a smarter replacement for the classical color-distance cutout heuristic.
  The model itself is fine, but it needs an ONNX runtime — pulled the actual npm package
  (`onnxruntime-web@1.27.0`) and its smallest WASM build is **13MB** (the only smaller variants
  need SharedArrayBuffer/cross-origin-isolation headers the site doesn't set). Roughly doubling
  the app's total download to improve cutout edges — which the classical heuristic already
  feathers reasonably — wasn't a good trade. Skipped.
- **Conclusion: RESEARCH.md's existing "photoreal try-on breaks zero-cost" verdict still holds**,
  now with concrete 2026 evidence (specific licenses, specific model sizes) instead of the
  vaguer prior finding. Worth folding into RESEARCH.md §2 in a future pass so the next session
  doesn't re-research this from scratch.

**What actually was fixable, and fixed, in `apps/silhouette-tryon/app.js` — classical
compositing, zero new dependencies:**
1. Removed a dashed white rectangle drawn around the whole overlay (originally meant as an
   honesty signal, "this is a sketch"). In practice it reads as a screenshot tool's selection
   marquee, not a sketch — the existing "PREVIEW — NOT A PHOTO" badge already carries that
   honesty burden without looking like a bug.
2. Added a real drop shadow, computed off the actual composited garment layer (not per warp
   triangle, which would seam at the triangles' shared diagonal — that internal edge is a hard
   clip boundary, not a real silhouette edge, and a naive per-triangle shadow would render it as
   a fake crease down the middle).
3. Added brightness/saturation harmonization: samples the selfie's luma under the garment and
   the garment's own luma, partially corrects the garment toward the photo's actual lighting
   (`HARMONIZE_STRENGTH = 0.55`, clamped) instead of pasting it at its native brightness
   regardless of context.
