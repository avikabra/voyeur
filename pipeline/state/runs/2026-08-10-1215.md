## Stage (c) Research — DONE

Confirmed the technical approach and its one real landmine:

- **Pose detection**: MediaPipe Tasks Vision `PoseLandmarker` (`@mediapipe/tasks-vision@1.0.1`,
  Apache-2.0), `pose_landmarker_lite` model (`.task` bundle, ~5.5MB, Apache-2.0 per the official
  BlazePose GHUM 3D model card — redistributable, no non-commercial restriction). Both the JS
  runtime and the wasm/model assets can be vendored (downloaded once, committed as static
  self-hosted assets) — Apache-2.0 explicitly permits this provided the license/attribution is
  preserved. `FilesetResolver.forVisionTasks()` and `PoseLandmarker.createFromOptions()` both
  accept same-origin relative paths, so no CDN dependency at runtime. Single-image detection is
  `detect()` (IMAGE mode) returning 33 normalized landmarks with x/y/z/visibility.
- **The landmine**: current `@mediapipe/tasks-vision` builds (through the current 1.0.1) contain
  an internal, undocumented telemetry beacon that attempts to phone home to Google's logging
  endpoint regardless of self-hosting the assets — open, unresolved upstream issues (#6291,
  #4991), no official opt-out. That's a direct conflict with PRINCIPLES ("no third-party
  scripts," "no trackers," "every asset served from our own deploy"). **Mitigation, decided
  here**: ship a strict same-origin CSP (`connect-src 'self'`, plus the narrowest other
  directives the app needs) via a `<meta http-equiv="Content-Security-Policy">` tag. This makes
  "zero network calls leave the browser" a property the *browser itself* enforces, not something
  that depends on correctly patching a minified vendored file — verifiable and robust, and it's
  the adversarial breaker's job later this run to confirm zero non-origin requests with a
  network-log check. This is a deviation worth recording as a durable technique: any future app
  vendoring a Google/Meta/etc. ML library should assume telemetry-by-default and enforce CSP
  rather than trust vendoring alone. *(Follow-up for docs: worth adding a line to
  ARCHITECTURE or PRINCIPLES about this pattern — not done in this commit, flagging for the
  next session or a dedicated docs pass.)*
- **Garment cutout, no ML needed**: e-commerce product photos are near-universally shot on
  plain/near-white backgrounds. A corner-sampled flood-fill (sample the four corner pixels,
  remove near-matching background color with a feathered edge) is a classical, zero-dependency
  technique that handles the actual target use case (a screenshot from a shop) without needing
  any segmentation model or bundled dataset.
- **The warp**: piecewise-affine mesh warp (split the garment quad into two triangles, solve the
  3-point affine matrix per triangle, `ctx.transform` + clip + `drawImage`) is well-understood
  classical graphics, implementable from scratch in vanilla canvas with zero libraries. It
  deliberately cannot fake fabric drape or occlusion — the plan is to render the result as an
  honestly-labeled stylized/semi-transparent overlay, never claiming photorealism, which sidesteps
  exactly the failure modes that make full photoreal try-on hard.

(Apache-2.0) from `registry.npmjs.org` and `storage.googleapis.com` (both reachable; `unpkg`/

a fact worth adding to OPERATIONS' hard-won-facts list). Wrote `LICENSE`/`NOTICE.md` for the
vendored directory. Both wave-1 agents (`cutout.js`, `warp.js`) delivered clean, well-verified
code on the first pass — `warp.js`'s author hand-derived and checked 5 affine-transform test
cases including one it invented itself (a rotation case) beyond what was asked; `cutout.js`'s
author stood up its own throwaway Playwright harness and verified 5 real scenarios in a real
browser, not just reasoning.

Integrated everything and drove the real build end-to-end with Playwright (headless Chromium,
pre-installed in this environment at `/opt/pw-browsers` — confirmed working directly, no need
for the `@sparticuz/chromium` npm workaround OPERATIONS describes from the pilot; noting this
too as possibly outdated environment info worth revisiting) against a real photo (a public
3-person test photo from `raw.githubusercontent.com`, used only for local testing, never
shipped) and a synthetic garment image. Two real bugs surfaced from this self-verification, both
fixed before handing to the adversarial loop:

1. The page's own strict CSP (`script-src 'self'`) blocked its own inline `<script>` that added
   the `.js` progressive-enhancement class — the whole app was stuck behind the "needs
   JavaScript" fallback message. Fixed by moving that one line to be the first statement in
   `app.js` (an external, CSP-permitted module script) instead, preserving the same
   fails-safe-to-no-js guarantee the shipped `vinted-size-decoder` app established.
2. Pose detection used `numPoses: 1` and used whichever pose the model returned first; in the
   3-person test photo it picked a seated bystander instead of the central standing subject.
   Fixed by detecting up to 5 poses and picking the one with the largest torso bounding box —
   a real robustness improvement for the very common case of someone else taking the photo.

Confirmed via Playwright: full flow (engine load → selfie → pose found → garment → background
removed → warped preview renders on the correct subject → sliders visibly adjust it → download
produces a file → reset returns to a clean state) works with **zero console errors and zero
non-origin network requests** — the CSP mitigation for the vendored library's known telemetry
call was directly verified to hold under real use, not just asserted.

## Stage (f) Adversarial loop — IN PROGRESS

Three parallel agents launched against the real running local build (not a code reading
exercise): a code reviewer (zero-network claim, license compliance, geometry-math correctness,
error-handling coverage, phone performance, accessibility), an adversarial breaker (empty/
garbage/huge/tiny inputs, offline-after-load, rapid clicking, keyboard nav, reduced motion,
exhaustive network-request audit), and simulated first-time users (four personas, 375-390px
viewport, real screenshots). This was not a clean first pass — good, per PIPELINE a suspiciously
clean round means the adversaries weren't hard enough. Real findings, most important first:

- **[Correctness]** `quadFromPose` derived image-left/right once from the shoulders and reused
  that flag for the hips too; a rotated or weight-on-one-hip pose (common, not exotic) could
  silently produce a twisted destination quad instead of an honest failure message.
- **[Performance, measured not guessed]** `landmarker.detect()` runs synchronously on the main
  thread; the code reviewer used CDP CPU throttling (4x) and measured a ~5.1s completely frozen
  frame gap, confirming the pre-existing 30ms yield is real (one paint before the freeze) but not
  a fix for the freeze itself.
- **[Correctness]** `renderPreview`'s own geometry/canvas glue wasn't fully guarded, unlike the
  never-throw guarantees `pose.js`/`cutout.js`/`warp.js` each document and the reviewer verified
  hold — a gap in an otherwise carefully defensive codebase.
- **[Honesty, non-negotiable per PRINCIPLES]** `manifest.json`'s `evidence` array was unlinked
  prose, not links — a real miss on my part at build time.
- **[Honesty]** the in-page "load this page with your network off... it still works" claim was
  verified true only for staying on the already-open tab; a genuine offline *reload* fails
  (confirmed via `curl -I`: no `Cache-Control` header anywhere, forcing revalidation that fails
  offline). The claim overstated what was actually shipped.
- **[Honesty/consistency]** the "struggles with more than one person in frame" limitation no
  longer matched actual behavior after the build-stage largest-torso-selection fix — a 3-person
  photo was accepted and worked, contradicting the app's own stated caveat.
- **[UX, first-time-user]** no auto-scroll/focus after a step unlocks — on a phone viewport,
  steps 2 and 3 were entirely off-screen after a successful upload with zero cue to scroll.
- **[UX]** success and failure status text were visually identical (same neutral gray) — real
  risk for a skimming user not registering that something needs fixing.
- **[Robustness, breaker]** a crafted SVG with an external `<image>` reference throws a raw
  `SecurityError` from `canvas.toBlob()` (canvas tainting per spec — confirmed zero network
  request ever actually fires) that leaked past the friendly-error path to the user.
- **[Robustness, breaker]** no guard against a small file declaring huge pixel dimensions (a
  PNG decompression-bomb pattern) before the existing byte-size cap could catch it — demonstrated
  a ~1.5GB memory spike from a 1.2MB file.
- Several accessibility nits (canvas with no accessible name, step headings skipping a heading
  level, no focus management between steps).
