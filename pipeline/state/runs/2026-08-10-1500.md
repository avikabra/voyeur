## Stage (d) Plan — DONE

- `pose.js` — wraps MediaPipe `PoseLandmarker`. `detectBodyLandmarks(imageSource)` →

## Stage (f) Adversarial loop — DONE, one real bug found and fixed

Ran this myself: code review, adversarial inputs, and simulated-first-time-user passes, all via
Playwright driving the actual running build (served locally with `npx serve`, Chromium via the
pre-installed `/opt/pw-browsers` binary), not a reading of the code.

**Real bug caught and fixed:** `garment.js`'s background-removal flood fill compared each
candidate pixel to the color of whichever *neighboring pixel* had just been accepted into the
background region, not to a fixed reference. On a synthetic test case (a solid-color shape on a
plain background) this walked straight through the shape's anti-aliased edge — a few pixels of
smooth color gradient is exactly what an adaptive/chained threshold can't resist — and flooded
the *entire* shape as "background," leaving `opaqueFraction` at ~1% instead of the true ~44% and
making `cutoutGarment` return `null` (falsely reporting "couldn't separate the garment"). Fixed
by switching every seed to test against its own *fixed* sampled color for the whole fill,
instead of the chained neighbor color. Re-verified: the synthetic case now gives the correct
~44.7% opaque fraction, and the real end-to-end photo test (below) still works. This also
happened to fix a performance problem in the same edit — the old code allocated a new 3-element
color array on every single pixel pushed onto the flood-fill stack; flattening the stack to
plain x/y numbers cut a 1600×1600 cutout from ~1.3s to ~0.36s (verified with `performance.now()`
in-page, not estimated).

**End-to-end real-photo test** (the VITON-HD teaser crops): pose detected correctly (shoulders
+ hips, high confidence), garment cutout succeeded, warp rendered a recognizable, correctly
positioned garment overlay with the dashed "this is schematic" outline — screenshotted and
visually confirmed, not just asserted programmatically.

**Adversarial inputs, all handled correctly with honest error messages, no crashes, no stale
state:** a `.txt` file renamed as an upload, a zero-byte file, a photo with no person in it (a
solid-color synthetic landscape), re-uploading a bad photo after a good render (correctly clears
the stale result instead of leaving it showing), "Start Over" (correctly resets file inputs,
thumbnails, and status text). Also tested: a real front-facing photo that was genuinely cropped
above the hips (a mirror selfie) — correctly rejected with "couldn't confidently find... hips"
rather than guessing; debugged with the raw MediaPipe output to confirm the hip landmarks
actually did have <0.06 visibility, i.e. the rejection was correct, not a bug.

**Mobile (375px) and dark mode**, both screenshotted: no horizontal overflow, layout holds,
dark-mode palette (separate CSS custom properties, no shared file with the JS logic) renders
correctly. **4x CPU-throttled** (Chrome DevTools Protocol) run of the full pipeline — model
init, pose detection, cutout, warp — completed in ~3.7s, which reads as acceptable for a
mid-range-phone estimate given the model only loads once and is then cached.

**CSP / privacy verified, not just asserted:** captured every network request the page made
during a full run — the only non-same-origin URLs were `blob:` object URLs (from the app's own
`URL.createObjectURL` on user-selected files), confirming zero data leaves the browser. Removed
`frame-ancestors` from the CSP `<meta>` tag after confirming it's a browser-logged no-op there
(frame-ancestors only has effect via a real HTTP header, not a meta tag) — cosmetic cleanup, not
a security change. Added `<label>`s (visually hidden) to both file inputs for screen readers —
a cheap, real accessibility gap the first pass missed.
